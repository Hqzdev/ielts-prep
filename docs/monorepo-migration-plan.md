# Veylo: план перехода к монорепозиторию и слоистой архитектуре

Дата плана: 2026-09-05. Статус: согласован и реализован локально 2026-09-06. Внешние настройки GitHub/хостинга перечислены в [отчёте](migration-report.md).

Цель: подготовить существующий Veylo к развитию веб-приложения и последующему добавлению нативных приложений для iOS и macOS. Сохранить пользовательские данные и текущие сценарии: авторизацию, задания, черновики, оценивание, разговор с Веем, словарь, Arcade и ежедневную серию.

## Исходное состояние до миграции

- Рабочее приложение находится в `web/`. Корневого workspace с несколькими пакетами пока нет; `web/pnpm-workspace.yaml` задаёт разрешения на сборку зависимостей.
- Есть `domain`, `server/services`, `server/repositories`, `client`, React-компоненты и Next.js Route Handlers. Это основа для миграции.
- Сценарии используют конкретные репозитории, `adminClient`, глобальную конфигурацию и иногда напрямую выполняют запросы. Необходимо отделить application от infrastructure через интерфейсы и внедрение зависимостей.
- `domain` содержит Zod-схемы, форматирование интерфейса и геометрию/анимацию персонажа. Эти ответственности нужно разнести.
- `workflows/assessment.ts` одновременно управляет workflow, обращается к БД и выполняет проверку. Use case оценивания должен быть отдельным от адаптера Workflow.
- HTTP-клиент `api<T>` использует ручную типизацию ответа; общего формального контракта для веба и Swift пока нет.
- Авторизация API связана с cookie-сессией Next.js. Для нативных клиентов потребуется проверка Bearer-токена и общий контекст пользователя.
- Есть Vitest, Playwright, SQL-проверки и 11 SQL-миграций. Репозиторные CI, CODEOWNERS, IaC и OpenAPI пока не обнаружены. JSON-логи ошибок частично присутствуют, общего контекста запросов и мониторинга нет.
- Python-генератор контента расположен в корне и не требуется для работы веб-сервера.
- На момент проверки `git ls-files` возвращает 0: перед массовыми переносами нужно подготовить безопасное исходное состояние Git.

## Архитектурное решение

Монорепозиторий с модульным серверным монолитом. Next.js первоначально остаётся средой исполнения веба и HTTP API. Серверные сценарии выделяются в пакет, независимый от Next.js, что позволяет позднее вынести API в отдельное приложение при реальной необходимости.

Предлагаемые модули: identity, catalog, practice, assessment, conversations, vocabulary, arcade, learning. Административные операции используют публичные сценарии этих модулей. Ежедневная серия относится к learning.

Правила зависимостей:

- `interfaces → application → domain`.
- `infrastructure` реализует интерфейсы, объявленные в application/domain, и зависит от них.
- `composition` создаёт конкретные адаптеры и передаёт их сценариям через конструкторы.
- Domain содержит бизнес-типы и правила, не импортирует Next.js, React, Supabase, Zod, HTTP-контракты и SDK провайдеров.
- Application не создаёт подключений, не читает `process.env` и не знает об HTTP, cookies или компонентах интерфейса.
- HTTP-адаптер валидирует контракт, получает проверенную личность пользователя и вызывает сценарий; ошибки domain/application переводятся в HTTP-коды на этой границе.
- Клиентские приложения используют API. Доступ к закрытым ключам заданий, административным ключам и бизнес-таблицам остаётся на сервере. Клиентские адаптеры Supabase Auth и подписанная загрузка файлов сохраняются как явно определённые интеграции.
- Между серверными модулями разрешены публичные интерфейсы и события с определённой схемой. Владение таблицами фиксируется; произвольный доступ к таблицам другого модуля запрещается.
- Транзакции, RLS, ограничения уникальности и защита от повторной записи остаются средствами PostgreSQL. Миграция архитектуры не должна ослабить их или создать два конкурирующих источника бизнес-правил.

## Целевая структура

```text
veylo/
  apps/
    web/
  packages/
    backend/
      src/
        domain/
        application/
        infrastructure/
        composition/
      tests/
    contracts/
    api-client/
    design-tokens/
    ui-web/
  tools/
    content-generator/
  infra/
    supabase/
  docs/
    adr/
    runbooks/
  scripts/
  .github/
  package.json
  pnpm-workspace.yaml
  pnpm-lock.yaml
```

Внутри серверных слоёв код группируется по перечисленным предметным модулям. Next.js-страницы и Route Handlers являются адаптерами interfaces. `packages/backend` предоставляет ограниченные публичные входы; глубокие импорты проверяются автоматически.

При начале разработки Apple-приложений добавятся `apps/ios`, `apps/macos` и Swift-пакеты для общего клиента API, сессии, синхронизации и дизайна. До этого их границы будут описаны в ADR, без пустых приложений.

pnpm управляет JS/TS-пакетами через workspaces. Python использует собственное зафиксированное окружение; Swift — Swift Package Manager и Xcode. Монорепозиторий объединяет исходники, контракты и проверки, а не заменяет инструментальные цепочки разных языков.

## Этапы работы

1. **Зафиксировать исходное состояние.** Проверить ignore-правила, исключить секреты, локальную базу, `.pnpm-store`, зависимости, кеши и сборки. Проверить содержимое будущего исходного коммита. Сохранить резервную копию БД и Storage, карту маршрутов и текущих сценариев. Снять исходный результат проверок; найденные проблемы отделить от последствий миграции.

2. **Собрать workspace.** Перенести `web` в `apps/web`, Python-генератор в `tools/content-generator`, конфигурацию Supabase с миграциями в `infra/supabase`. Сохранить идентичность локального проекта Supabase и существующие данные. Обновить относительные пути, загрузку контента, переменные окружения, копирование VAD, команды запуска и тестов. Переносы отделить от изменения поведения. Зафиксировать версии Node.js/pnpm и единый JS/TS lockfile.

3. **Установить проверяемые границы.** Подготовить ADR, схему модулей, публичные exports, интерфейсы репозиториев, AI, файлового хранилища, очереди, часов и генератора идентификаторов. Добавить проверки запрещённых импортов и циклов. Не создавать абстракции для единственной чистой функции или общего контейнера `utils` без определённого назначения.

4. **Перенести бизнес-логику вертикальными частями.** Сначала каталог и practice, затем learning/серия и vocabulary, затем assessment, conversations/audio и Arcade. Для каждой части: чистые правила, application-сценарии, адаптеры, подключение HTTP/UI, проверки и удаление прежнего пути выполнения. Схемы входных данных отделить от доменных сущностей. Сохранить идентификаторы, версии заданий, таймеры, историю и семантику ошибок.

5. **Оформить общий API.** Создать OpenAPI 3.1.0 и `/api/v1`, документировать ошибки, пагинацию, версии черновиков, даты, часовые пояса и идемпотентность повторяемых операций. Описать потоковые события чата, отмену ответа и аудиозагрузку отдельными явными схемами. Сгенерировать типизированный TS-клиент и проверять совместимость контракта в CI. Старые маршруты на время перехода будут тонкими адаптерами к тем же сценариям, затем удалятся после перевода всех текущих потребителей.

6. **Подготовить API к нативной авторизации.** Отделить получение пользователя из веб-cookie от верификации access token нативного клиента. Для обоих путей использовать одни проверки доступа и владения данными. Проверить истёкшие токены, обновление сессии, выход, отзыв доступа и повтор сетевого запроса. PKCE, OAuth callback/deep links и Keychain описать в контракте будущего Apple-клиента; реализацию приложений выполнять позже.

7. **Разделить интерфейс и платформенные механизмы.** Учебные экраны оставить в приложении, повторно используемые веб-компоненты и SVG-Вея выделить в `ui-web`. Цвета, размеры, радиусы, типографику, ассеты и параметры движения оформить как общие дизайн-данные. Web Audio, VAD, IndexedDB и DOM остаются веб-адаптерами. Будущие SwiftUI-экраны получают собственные адаптеры микрофона, хранения и отрисовки. Общими остаются значения и смысл состояний Вея, а не React/DOM-код.

8. **Привести код и инструменты к соглашениям.** Общие ESLint/Prettier/TypeScript-конфигурации для TS; Black/Ruff для Python; инструмент форматирования Swift при появлении Swift-кода. Настроить pre-commit, Conventional Commits и проверки CI. Делить функции и классы по ответственности, выносить значимые числа в именованные настройки, удалить подтверждённо неиспользуемые зависимости. Правило примерно 40 строк использовать как сигнал для ревью. Сохранить ранее заданный запрет комментариев в собственном коде: причины решений записывать в ADR. Именование учитывать по языку: kebab-case для TS/CSS, допустимые имена импортируемых Python-модулей и обязательные имена файлов инструментов.

9. **Подготовить командную работу и эксплуатацию.** Назначить реальных владельцев в CODEOWNERS; настроить небольшие PR, один обязательный approve и два для критичных путей при наличии соответствующих ревьюеров, обязательные проверки перед merge. Добавить шаблон PR с причиной, проверками и визуальными материалами. Для выбранного хостинга описать dev/staging/production, IaC, секреты, staging smoke и отдельное одобрение production. Расширить JSON-логи request ID и длительностями, добавить метрики ошибок/задержек/очереди/AI-запросов и точки трассировки. Не записывать токены, аудио и учебные тексты в технические логи. Подготовить запуск, деплой, откат и восстановление в runbooks.

10. **Принять миграцию.** Проверить установку с нуля, unit, контрактные и SQL/integration-тесты, сборку и основные браузерные сценарии. Подтвердить сохранение авторизации, черновиков, результатов, чата, аудио, серии и анимаций. Проверить независимость domain/application от Next.js и БД, отсутствие старых импортов и дублированных реализаций. Проверить генерацию и компиляцию минимального Swift API-клиента в изолированной проверке совместимости, без создания пользовательского приложения. Новый разработчик должен запускать проект по README не более чем за пять команд после установки системных зависимостей.

Изменения выполнять небольшими законченными PR; механические переносы отделять от логики. Conventional Commits дополняются реальной настройкой генерации changelog/release, сами сообщения автоматический выпуск не создают.

## Случаи, которые нельзя потерять при переносе

- Повторная сдача работы или сохранение раунда не создают повторного результата и огонька.
- Строгий дедлайн и конфликт ревизий черновика остаются серверными.
- Переход даты, часовой пояс, пропуск дня и повтор события сохраняют правильную серию.
- Завершение браузерной сессии не отменяет уже поставленное оценивание.
- Ошибки AI, обрыв стрима, отсутствие речи и отказ микрофона остаются различимыми состояниями.
- Пользователь не получает чужие данные, ключи Reading и приватное аудио.
- Старые клиенты сохраняют работоспособность в пределах опубликованной версии API.
- Откат приложения совместим с миграциями БД; удаление данных и изменение схемы требуют отдельного безопасного перехода.

## Предлагаемые технологии для подготовки и Apple-приложений

- Монорепозиторий: pnpm workspaces и зависимости `workspace:`; корневые команды запуска и проверки. Дополнительный оркестратор сборки выбирать только по измеренной необходимости.
- API: OpenAPI 3.1.0, генерация TS-клиента, Swift OpenAPI Generator для Swift-клиента. Контракт является источником истины для DTO; runtime-валидация и обработчики проверяются на соответствие ему.
- Apple-приложения позднее: Swift, SwiftUI, Xcode, Swift Package Manager, URLSession/Swift Concurrency, Keychain, AVFoundation; Swift Testing и XCTest/XCUITest. Точные версии и минимальные версии ОС фиксируются при старте нативной разработки.
- Общий дизайн: версионируемые JSON-токены/ассеты с генерацией CSS и Swift-значений.
- Автоматизация: GitHub Actions при размещении репозитория на GitHub; проверка границ, контрактов, линта, типов, тестов и сборки. Подпись и доставка Apple-приложений добавляются на этапе их разработки.
- Инфраструктура: Supabase/PostgreSQL остаются; Vercel является текущим кандидатом для Next.js/Workflow. Конкретный IaC-провайдер и хранилище секретов фиксируются вместе с выбором hosting и окружений.

Внешние решения для полного внедрения: размещение Git-репозитория, реальные владельцы и ревьюеры, выбранные staging/production-проекты и доступы. Готовность этих настроек проверяется отдельно от готовности локальной структуры кода.
