# Развёртывание и открытие беты

## Окружения

Local работает с Docker Supabase. Для staging и production нужны два отдельных проекта Supabase и отдельные переменные окружения Vercel. Не копировать локальные аккаунты, записи, историю и результаты тестов в production.

1. Создать внешний Supabase-проект. Применить все миграции из `infra/supabase/migrations` последовательно через Supabase CLI (`link`, затем `db push`) для выбранного проекта.
2. Настроить email confirmation, пароль от десяти символов, site URL и разрешённый callback `<APP_URL>/auth/callback`. Включить Google OAuth, задать client ID и secret, добавить callback Supabase в Google Cloud.
3. Настроить собственный SMTP Resend в Supabase Auth: подтверждённый отправитель, host, порт и SMTP credentials. Настройки хранятся у провайдера, а не в клиентском коде. [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).
4. В Vercel выбрать Root Directory `apps/web`, Node.js 24, pnpm install и Next.js build. Перенести значения из `.env.example` в нужное окружение. Все секреты серверные; публичными остаются только URL Supabase и publishable key.
5. Задать `APP_URL`, случайный `CRON_SECRET`, лимиты беты, ключ Gemini и модели. До калибровки держать флаги оценивания выключенными.
6. Запустить `pnpm db:seed` с переменными целевого проекта. Команда импортирует контент и слова; локальный аккаунт создаётся только для loopback Supabase.
7. Зарегистрировать и подтвердить адрес владельца. Выполнить `pnpm admin:invite --email owner@example.com --promote` с сервисным ключом целевого проекта. Команда меняет роль только указанного существующего подтверждённого аккаунта.
8. Выдавать приглашения в `/admin` либо через `pnpm admin:invite --email learner@example.com`. Команда и UI создают ссылку со сроком семь дней, сами не отправляют письма.

## Фоновая обработка

Vercel Workflow обслуживает оценивание. Папку маршрутов `.well-known/workflow` создаёт сборка; не редактировать её вручную. Диспетчер запускается после сдачи и повторяется через `/api/maintenance`. Закрытие пользовательской вкладки не прерывает процесс.

`vercel.json` задаёт обслуживание раз в минуту. Для размещения нужен тариф/окружение Vercel, допускающее такую частоту Cron и Workflow. Проверить доступность перед запуском; если выбранное окружение не поддерживает её, настроить эквивалентный защищённый scheduler. Обработчик принимает только `Authorization: Bearer <CRON_SECRET>`.

Maintenance удаляет истёкшее аудио, фиксирует строгие попытки после дедлайна, поднимает задания очереди и обнаруживает завершившиеся с ошибкой Workflow. Повторный запуск безопасен. Локально автоматический Vercel Cron не запускается: для проверки вызвать endpoint вручную через серверный скрипт с секретом в окружении.

## Резервные копии

Настроить резервное копирование внешнего Supabase до приглашения учеников. База и файлы Storage восстанавливаются раздельно: SQL-дамп не содержит сами WAV. Зафиксировать допустимую потерю данных и время восстановления в настройках эксплуатации.

Локальная проверка 03.09.2026: `pg_dump` схем `auth` и `public`, восстановление через `pg_restore` в отдельную временную базу, сверка 146 заданий, 300 слов, соответствия auth users/profile и включённого RLS. Временная база и дамп удалены после проверки. Это проверка механизма восстановления; внешнее резервное копирование ещё не настроено.

При восстановлении создавать пустую отдельную базу, подготовить нужные extensions и роли, восстановить схемы и данные, проверить RLS и закрытость buckets, затем проверить обычный вход и собственную попытку. Сначала восстановить staging; переключение production делать отдельно после сверки.

## Проверенные сценарии

Локально проверены импорт без дубликатов, ключи всех Reading-форматов, черновики, серверные дедлайны, повторная сдача, исправление, разделение пользователей, закрытое аудио, пауза Speaking, обработка речи/тишины/шума, отсутствие AI-ключей и сохранение результата. Проверены сборка, TypeScript, ESLint, Vitest, Chrome и WebKit.

Нагрузка: десять одновременных локальных пользователей создавали попытку, сохраняли ответ и ставили одну проверку в очередь. Дубликаты не создавались, ошибок не было. Измерения находятся в `.local/load-report.json`; это локальный dev-сервер, а не обещание production latency.

## Оставшиеся внешние проверки

- Google OAuth с настоящими credentials и письма через настроенный Resend.
- Реальные запросы проверки, транскрипции, TTS и чата после добавления Gemini key.
- Экспертная калибровка каждой включаемой части по `assessment-quality.md`.
- Workflow и Cron на выбранном Vercel deployment, включая закрытие вкладки и временную ошибку провайдера.
- Физический микрофон и наушники, Safari и Edge на целевых компьютерах. Автоматизированный WebKit не равен проверке установленного Safari.
- Резервное копирование и восстановление внешней базы и Storage.

До этих проверок приложение является работающей локальной реализацией беты; публичный доступ и достоверность учебного band не заявляются готовыми.
