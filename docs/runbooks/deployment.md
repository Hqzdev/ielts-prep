# Деплой и откат

## Окружения

Dev — локальный Docker Supabase и Next.js. Для staging и production нужны отдельные проекты Supabase, отдельные ключи и данные. В репозитории сохранена конфигурация Vercel Cron; origin указывает на публичный Hqzdev/ielts-prep. Основная ветка для публикации — `main`; реальные cloud project ID и домены не назначены. Provisioning облачных ресурсов и автоматический CD до их выбора не выполнены.

При использовании Vercel Root Directory — `apps/web`, установка workspace выполняется из корня репозитория по закреплённому pnpm lockfile. Build приложения — `pnpm --filter @veylo/web build`. Разрешить включение файлов вне Root Directory, чтобы доступны были backend/contracts/ui-web/design-tokens. Node — 24. Конфигурация Cron находится в `apps/web/vercel.json`.

## Подготовка выпуска

1. Получить зелёный Verify на точном commit: формат, слои, контракт, типы, unit, SQL/integration, браузеры, Swift. Применённые SQL-файлы не переписывать; изменения базы оформлять новой миграцией.
2. В выбранном staging Supabase применить миграции из `infra/supabase/migrations` через CLI `--workdir infra`, с явно выбранным project ref. До применения снять резервную копию базы и Storage. Сервисные ключи передаются через секреты окружения.
3. Настроить Auth site URL, разрешённые callback, email и Google-провайдер. `APP_URL` должен точно соответствовать окружению. Не переносить локальные тестовые аккаунты в облако.
4. Собрать и развернуть тот же commit в staging. Внести переменные из `apps/web/.env.example` в секреты выбранного окружения. Writing/Speaking-оценивание включать только после проверки качества.
5. Проверить вход, reload черновика, Reading-результат, quiz и серию, закрытость чужой попытки и signed audio URL. Для AI отдельно проверить реальную транскрипцию/TTS/чат и завершение фоновой проверки после закрытия вкладки.
6. Настроить защищённый scheduler `/api/maintenance` с `Authorization: Bearer <CRON_SECRET>` и проверить повторный запуск. Частота раз в минуту и Workflow должны поддерживаться выбранным тарифом/средой.
7. После staging smoke получить отдельное одобрение production и развернуть тот же проверенный commit. Зафиксировать commit, deployment ID, версии миграций и время переключения в журнале выпуска.

После выбора провайдеров provisioning, секретные ссылки и promotion следует закрепить в IaC и GitHub environments с approval production. До этого этот runbook описывает порядок действий, а не существующий автоматический deployment.

## Откат

При ошибке приложения переключить deployment на предыдущий проверенный commit. Миграции делать по принципу expand/contract: предыдущая версия приложения должна работать с расширенной схемой. Не запускать обратную SQL-миграцию или db reset на базе с пользовательскими данными ради отката интерфейса.

Если повреждены данные, остановить затронутые записи и восстановить отдельное окружение по recovery runbook; только после сверки переключать трафик. Повторная отправка assessment должна использовать прежний ID и существующие ограничения очереди.

## Внешние незавершённые действия

CODEOWNERS уже назначен @Hqzdev. Нужны второй ревьюер, подтверждённый хостинг, staging/production project ID и secret store. Публикация commit в origin не разворачивает сайт. После этого можно включить branch protection, cloud IaC, CD, резервное копирование и dashboard метрик. Локальная миграция этих внешних настроек не заменяет.
