# Резервное копирование и восстановление

Перед архитектурной миграцией сохранены полная локальная PostgreSQL-база в custom pg_dump и файлы Storage. Они лежат в игнорируемой `.local/migration-backup` с доступом только владельцу. Дампы, содержимое пользовательских таблиц и Storage не коммитятся и не прикладываются к PR.

Для текущего локального проекта контейнер базы — `supabase_db_ielts-prep`. Идентификатор проекта в `infra/supabase/config.toml` сохранён, поэтому перенос каталога не создал новую базу. SQL-миграции перенесены без изменения применённых файлов.

## Создание резервной копии

Согласовать согласованный момент снимка базы и файлов: остановить новые записи на время экспорта либо использовать согласованные snapshots провайдера. Сохранить `pg_dump --format=custom`, Storage-объекты, идентификатор commit, список применённых миграций и версии PostgreSQL/extensions. Хранить в закрытом зашифрованном хранилище с ограничением доступа. Срок хранения, RPO и RTO назначаются для реального окружения.

## Проверка восстановления

1. Создать отдельную пустую тестовую базу и отдельное хранилище, совместимые по версии, extensions и ролям. Не восстанавливать поверх рабочей базы.
2. Восстановить схему и данные через pg_restore. Восстановить файлы Storage отдельно; SQL содержит метаданные, не бинарное аудио.
3. Сверить количество пользователей, попыток, результатов, учебных дней и файлов; проверить ссылки task version/attempt/assessment, состояние очереди, RLS и закрытость buckets.
4. На изолированном приложении проверить вход, чтение своей попытки и запрет чужой, воспроизведение подписанного аудио, сохранение нового черновика и повторный submit.
5. Записать фактическое время восстановления и расхождения. Переключать production только после отдельного согласования результата.

`pnpm test:sql` проверяет инварианты в транзакции и откатывает свои фикстуры. Эта команда не проверяет резервное копирование облака. `supabase db reset` не является шагом восстановления работающей пользовательской среды.
