# Работа с Veylo

Короткие ветки от main, небольшие законченные изменения, Conventional Commits. Для Codex используется префикс `codex/`. Обычный PR ориентирован на 400 строк содержательных изменений; разовый перенос монорепозитория требует отдельного обзора по слоям и не задаёт размер последующих PR.

Перед нетривиальной реализацией согласуется план. Класс и модуль имеют одну ответственность, зависимости передаются через композицию. Комментарии в собственном коде не добавляются; основания решений — в ADR. Функции длиннее примерно 40 строк требуют внимания на ревью, а не формального дробления ради числа.

JS/TS используют корневые ESLint, Prettier и TypeScript. Python — Black/Ruff из закреплённого uv-окружения с корневой конфигурацией. Swift-проверка форматируется `swift format`. Файлы TS называются kebab-case; Python-модули используют допустимые имена с подчёркиваниями, Swift — принятые имена типов.

`pnpm install` подключает versioned Git hooks. Pre-commit проверяет рабочие файлы без автоматического исправления или staging. Он не заменяет CI, поскольку проверяемый commit может отличаться от незакоммиченных файлов. Build, unit, integration и E2E остаются обязательными в Verify. Сгенерированные SDK, CSS и ассеты проверяются генераторами, сторонние лицензии и ранее применённые SQL-миграции не форматируются.

## Владение

Пакет — единица ответственности. Владелец существующего origin Hqzdev/ielts-prep подтверждён через GitHub: @Hqzdev, текущая учётная запись имеет ADMIN. CODEOWNERS покрывает все пакеты этим владельцем. Второй ревьюер для критичных путей ещё не назначен; его нельзя заменить повторным approve владельца.

| Область                                                                | Ответственность владельца                        |
| ---------------------------------------------------------------------- | ------------------------------------------------ |
| `apps/web`, `packages/ui-web`, `packages/design-tokens`                | Интерфейс, доступность, браузерное аудио, дизайн |
| `packages/backend`                                                     | Правила обучения, доступ, AI и фоновые задания   |
| `packages/contracts`, `packages/api-client`, `tools/api-compatibility` | Совместимость API и клиентов                     |
| `infra/supabase`                                                       | Миграции, RLS, транзакции, резервное копирование |
| `tools/content-generator`                                              | Генерация и проверка учебных материалов          |
| `.github`, `scripts`, корневые конфигурации                            | Инструменты, CI и выпуск версий                  |

Для GitHub main нужно включить обязательные Verify/web, Verify/python и Verify/swift, минимум один approve, сброс старых approve после новых изменений и запрет force push. Для auth/данных требуются два approve; сам CODEOWNERS не задаёт разное число approve для путей, это нужно настроить правилами репозитория/процессом ревью. Настройки не считаются включёнными до проверки на реальном репозитории.

## Выпуски

Release Please формирует PR с версией и CHANGELOG по Conventional Commits, затем tag/release после его слияния. Частные workspace-пакеты не публикуются в npm. Для автоматического запуска CI у release-PR нужен `RELEASE_PLEASE_TOKEN` с правами выбранного репозитория либо GitHub App; с обычным GITHUB_TOKEN созданные ботом события не запускают следующий workflow. В этом случае Verify запускается вручную на release-ветке до merge. Ни один release не разворачивает production автоматически.

## Контрактные изменения

Сначала измените Zod-схему и описание операции, затем сценарий/адаптер и клиент. Выполните `pnpm api:generate`, типы, интеграционные проверки и Swift-check. Удаление или смена типа обязательного поля требует новой версии API либо согласованного перехода всех клиентов. Проверка совпадения сгенерированных файлов сама по себе не доказывает обратную совместимость.
